# 0001 - JWT RS256 em vez de HS256

**Status**: Accepted

## Context

O backend Go precisa emitir e validar tokens de acesso para autenticação de usuários (`pkg/auth`, `auth.NewJWTService`). A escolha do algoritmo de assinatura JWT afeta como chaves são gerenciadas e quais serviços podem validar tokens de forma independente.

## Decision

Usar RS256 (assinatura assimétrica RSA) em vez de HS256 (HMAC com segredo simétrico). O serviço mantém um par de chaves RSA (`backend/keys/`, gerado via `make keys`) — a chave privada assina os tokens, a pública valida.

Alternativa considerada: HS256 com um segredo compartilhado. Rejeitada porque exigiria distribuir o mesmo segredo simétrico para qualquer serviço que precise validar tokens (hoje só o próprio backend, mas a separação já evita acoplamento futuro) — com RS256, a chave pública pode ser distribuída livremente sem risco de forjar tokens.

## Consequences

- Chave privada (`backend/keys/private.pem` ou equivalente) nunca pode ser commitada no repositório — gerada localmente via `make keys`, fora do controle de versão
- Rotação de chave é mais trabalhosa que HS256 (troca de par assimétrico, não só um segredo), mas não é uma operação frequente
- `auth.NewJWTService(privKey, pubKey, expiry)` recebe os dois componentes explicitamente — qualquer novo serviço que precise só validar (não emitir) tokens usa apenas a chave pública
- Claims JWT: `{owner_id: uuid, exp, iat}`, expiração de 15 minutos — tokens de curta duração combinados com refresh token (ver [0002](./0002-refresh-token-hash-2fa-temp-token.md))
